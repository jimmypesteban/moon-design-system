## Read this as "what do I already get"

The list above names the component behind each landmark, because the
useful question is rarely *what does `<nav>` mean*. It is **do I get one
already, or do I have to write it** — and mostly you do:

- **`AppLayout`** renders the `<main id="main-content">`. There should be
  exactly one `<main>` on a page, so if you are using `AppLayout` you already
  have it, and adding another is a bug rather than an improvement.
- **`TopNav`, `Breadcrumb`, `Pagination` and `StepperNav`** each render a
  `<nav>`. Several can legitimately appear on the same page.
- Everything else — `<header>`, `<section>`, `<article>`, `<aside>`,
  `<footer>` — you write yourself.

## Two rules that are easy to get wrong

**More than one `<nav>` needs labels.** A screen reader lists landmarks by
role, so three unlabelled navigations are announced as "navigation,
navigation, navigation". Each of ours carries an `aria-label` —
`"Breadcrumb"`, `"Pagination"`, `"Wizard steps"`, `"Main"` — which is what
turns that list into something usable. If you hand-roll a `<nav>`, label it.

**`<section>` is mostly not a landmark at all, and that surprised us.** A
`<section>` is exposed as a `region` landmark *only* when it carries an
accessible name — `aria-label` or `aria-labelledby`. Without one it is a
generic container, indistinguishable from a `<div>` to assistive tech. Same
rule for `<form>`. And `<article>` is `role="article"`, which is not a
landmark in the first place.

Counting tags therefore overstates our coverage by roughly **three times**. Of
419 `<section>` and 49 `<form>` elements across `apps/`, **twenty carry a
name** — so 448 of them are structure in the source and nothing in the
accessibility tree. The real figure is **234 landmarks**, not the 654 a grep
reports.

The fix is one attribute where the region is genuinely a themed area
(`<section aria-labelledby="…">` pointing at its heading), and `<div>`
everywhere else. Reaching for `<section>` because it feels more semantic than
`<div>` buys a screen-reader user nothing at all.

## Beyond landmarks

Landmarks are only the outermost layer. Four other families carry meaning
*inside* a page, and counting them across `apps/` shows where we are fine and
where we are not. These are not regions, which is why they are a table here
rather than parts of the wireframe above — they live *inside* a landmark.

One that looks like a gap and is not: **`<dialog>` is used 0 times**, because
`Modal` implements `role="dialog"` with `aria-modal` and its own focus trap
instead. That is a deliberate choice — the native element's focus and
backdrop behaviour is still awkward across browsers — not an oversight.

**`<search>` is also 0**, and that one is simply unused: it is the newer
element for a search region, and `role="search"` on a named `<form>` does the
same job in browsers that do not know it yet.

## Why bother

A landmark is not decoration; four different consumers read it.

- **Screen readers** build a landmark list, which is how a keyboard user skips
  the nav on every single page instead of tabbing through it.
- **Search engines** weigh content inside `<main>`/`<article>` differently from
  chrome inside `<header>`/`<footer>`.
- **AI crawlers and readers** use the same signals to decide what a page is
  actually about, which increasingly decides how it gets summarised.
- **The next developer** reads structure faster than they read class names.
